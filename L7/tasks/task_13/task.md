# L7 / Task 13 — Юниты

Маленькая пошаговая игра на клетчатом поле. Есть три вида юнитов: **игрок** ходит и получает урон, **башня** стоит на
месте и гасит часть урона бронёй, **стена** стоит на месте и просто получает урон. Программа выполняет команды: создать
юнита, сходить, ударить, взорвать бомбу, показать всех.

Главное в задаче — **как собраны типы**. Мы не пишем три независимых типа с повторяющимся кодом. Мы собираем их из
готовых деталей через **встраивание**, как машину из двигателя и колёс.

## Зачем эта задача

- Понять встраивание по-настоящему. Встроенная структура приносит **поля и методы**, а вместе с ними — подходящие
  интерфейсы. Код «здоровья» пишется один раз и работает у всех трёх юнитов.
- Увидеть, что встраивание приносит **все** методы детали. Поэтому решать, что встраивать, надо осознанно: стена не
  встраивает «умение ходить», и поэтому ходить не умеет.
- Научиться **закрывать** метод детали своим: у башни свой `TakeDamage` (с бронёй), который внутри вызывает «обычный» из
  детали.
- Собрать интерфейс из интерфейсов (встраивание интерфейсов) и проверить «умеет ли юнит ходить» через утверждение типа
  `u.(Mover)`.
- Так вообще-то пишут настоящие игрушки. Ну, может где-то код чуть посложнее :)

## Детали

Напиши ровно такие типы и методы:

```go
// Position — где стоит. Двигаться НЕ умеет.
type Position struct {
    X, Y int
}
func (p Position) DistTo(x, y int) int // расстояние «по клеткам»: |p.X - x| + |p.Y - y|

// Mobile — умеет ходить. Встраивает Position.
type Mobile struct {
    Position
}
func (m *Mobile) Move(dx, dy int) // X += dx, Y += dy

// Health — здоровье.
type Health struct {
    HP, MaxHP int
}
func (h *Health) TakeDamage(d int) // HP -= d, но HP не опускается ниже 0
func (h *Health) Alive() bool      // HP > 0
```

## Юниты

```go
type Player struct { // игрок: имя + умеет ходить + здоровье
    Name string
    Mobile
    Health
}

type Tower struct { // башня: имя + стоит на месте + здоровье + броня
    Name string
    Position
    Health
    Armor int
}

type Wall struct { // стена: имя + стоит на месте + здоровье
    Name string
    Position
    Health
}
```

У `Tower` есть **свой** метод `TakeDamage(d int)` с получателем `*Tower`. Он уменьшает урон на `Armor` (но не ниже 0) и
вызывает встроенный: `t.Health.TakeDamage(d)`. Свой метод **закрывает** одноимённый метод встроенного `Health`: вызов
`t.TakeDamage(5)` попадает в метод башни.

`DistTo` у игрока работает «сквозь» два уровня: `Player` → `Mobile` → `Position`. Писать `p.Mobile.Position.DistTo` не
нужно, достаточно `p.DistTo`.

У каждого юнита — метод `String() string` (получатель-указатель):

```
<вид> <имя> (<X>,<Y>) HP <HP>/<MaxHP>
```

где `<вид>` — `игрок`, `башня` или `стена`. Если юнит уничтожен (`HP == 0`), в конце добавляется ` [уничтожен]`
(через пробел). Броня башни в строке не печатается.

## Интерфейсы

```go
type Mover interface {
    Move(dx, dy int)
}

type Damageable interface {
    TakeDamage(d int)
    Alive() bool
}

type Locatable interface {
    DistTo(x, y int) int
}

// Unit собран из других интерфейсов — это встраивание интерфейсов
type Unit interface {
    Damageable
    Locatable
    fmt.Stringer
}
```

`Unit` требует все методы трёх интерфейсов: `TakeDamage`, `Alive`, `DistTo` и `String`. Записать интерфейс через
другие интерфейсы — то же самое, что перечислить их методы, только короче. Так в стандартной библиотеке собран
`io.ReadWriter` из `io.Reader` и `io.Writer`.

`*Player`, `*Tower` и `*Wall` реализуют `Unit`, а `Mover` — **только** `*Player`: метод `Move` пришёл к нему из `Mobile`.

## Команды

Ввод — команды до конца ввода. Юнитов может не быть совсем: тогда `status` ничего не печатает. Имена — одно слово, уникальные. Координаты и сдвиги — целые, могут быть отрицательными.
Здоровье при создании больше 0, броня и урон — не меньше 0. Ввод всегда корректный.

| Команда                          | Что делает и печатает                                                                                       |
|----------------------------------|-------------------------------------------------------------------------------------------------------------|
| `player <имя> <x> <y> <hp>`      | создаёт игрока с `HP = MaxHP = hp`, печатает его `String()`                                                 |
| `tower <имя> <x> <y> <hp> <armor>` | создаёт башню с `HP = MaxHP = hp` и бронёй `armor`, печатает `String()`                                  |
| `wall <имя> <x> <y> <hp>`        | создаёт стену с `HP = MaxHP = hp`, печатает `String()`                                                      |
| `move <имя> <dx> <dy>`           | сдвигает юнита, печатает его `String()`                                                                     |
| `hit <имя> <урон>`               | наносит урон, печатает `String()`                                                                           |
| `boom <x> <y> <r> <урон>`        | наносит урон всем **живым** юнитам, у которых `DistTo(x, y) <= r`. Печатает `взрыв задел: <сколько>`, затем по строке на каждого задетого: два пробела и его `String()` после урона |
| `status`                         | печатает `String()` всех юнитов                                                                             |

Порядок юнитов в `boom` и `status` — порядок создания.

Отказы `move` и `hit` проверяются в таком порядке. Первый сработавший печатается, и команда на этом заканчивается.
Это обычные строки вывода: `main` проверяет условие и печатает строку, тип `error` здесь не нужен.

1. юнита с таким именем нет — `нет юнита <имя>`;
2. юнит уничтожен — `<имя> уничтожен`;
3. только для `move`: юнит не умеет ходить (не `Mover`) — `<имя> не умеет ходить`.

## Пример

Ввод:

```
player Аня 0 0 10
tower Т1 2 0 20 3
wall W 5 5 30
move Аня 1 1
move W 1 0
hit Т1 5
boom 1 0 2 4
hit Аня 100
move Аня 1 0
move Боб 1 1
status
```

Вывод:

```
игрок Аня (0,0) HP 10/10
башня Т1 (2,0) HP 20/20
стена W (5,5) HP 30/30
игрок Аня (1,1) HP 10/10
W не умеет ходить
башня Т1 (2,0) HP 18/20
взрыв задел: 2
  игрок Аня (1,1) HP 6/10
  башня Т1 (2,0) HP 17/20
игрок Аня (1,1) HP 0/10 [уничтожен]
Аня уничтожен
нет юнита Боб
игрок Аня (1,1) HP 0/10 [уничтожен]
башня Т1 (2,0) HP 17/20
стена W (5,5) HP 30/30
```

Разбор: `hit Т1 5` — броня 3, урон 2, HP 18. Взрыв в (1,0) радиусом 2: до Ани (1,1) расстояние 1, до башни (2,0) — 1,
до стены (5,5) — 9. Аня теряет 4, башня — 4 − 3 = 1. `hit Аня 100` опускает HP до 0, а не до −94.

## Как решать

- Типы, поля и методы — ровно как выше. Методы `TakeDamage`, `Alive`, `Move`, `DistTo` пишутся **один раз** в деталях.
  У `Player` и `Wall` их нет: они приходят из встроенных структур. Своя версия есть только у `Tower.TakeDamage`.
- Юнитов храни в слайсе `[]Unit` (порядок создания) и в `map[string]Unit` (поиск по имени). Кладутся указатели:
  `&Player{...}`.
- В `boom`, `hit` и `status` не должно быть проверок конкретного типа: только методы интерфейса `Unit`.
- В `move` проверяй умение ходить утверждением типа: `m, ok := u.(Mover)`. Проверять по имени типа или через
  `switch u.(type)` с перечислением `*Player`, `*Tower`… нельзя: тогда при новом ходячем юните придётся править `move`.
- **Обязательно** добавь проверки при компиляции (что это такое — в [task_12](../task_12/task.md)):

  ```go
  var (
      _ Unit  = (*Player)(nil)
      _ Unit  = (*Tower)(nil)
      _ Unit  = (*Wall)(nil)
      _ Mover = (*Player)(nil)
  )
  ```

## Подсказки

- Литерал игрока со встроенными структурами: имя поля встроенной структуры — имя её типа:

  ```go
  &Player{
      Name:   "Аня",
      Mobile: Mobile{Position: Position{X: 0, Y: 0}},
      Health: Health{HP: 10, MaxHP: 10},
  }
  ```

- Модуль числа напиши своей маленькой функцией `abs(x int) int`.
- Вызвать метод детали, который закрыт своим, можно по полному имени: `t.Health.TakeDamage(d)`. Если в методе башни
  написать просто `t.TakeDamage(d)`, метод вызовет сам себя бесконечно, и программа упадёт с переполнением стека.
- В `String()` удобно собрать общую часть в одну функцию, например
  `state(kind, name string, p Position, h Health) string`, и вызывать её из трёх методов.

## Проверь себя

1. Почему стена не умеет ходить, хотя у неё есть координаты?
   <details><summary>Ответ</summary>

   Координаты (`Position`) и умение ходить (`Mobile`) — разные детали. Стена встраивает только `Position`. Если бы стена
   встроила `Mobile` «ради координат», вместе с ними она получила бы метод `Move`, стала бы `Mover` и начала бы ходить.
   Встраивание приносит **всё**, поэтому детали делают маленькими, а встраивают только то, что нужно.
   </details>

2. Можно ли передать `*Player` в функцию `func heal(h *Health)`? А `&p.Health`?
   <details><summary>Ответ</summary>

   `heal(p)` — нельзя: `*Player` не является `*Health`, в Go нет наследования. Встраивание не делает игрока «разновидностью
   здоровья», оно делает здоровье **частью** игрока. А `heal(&p.Health)` — можно: это адрес самой части. А вот в функцию,
   которая принимает **интерфейс** `Damageable`, игрок передаётся: методы-то у него есть.
   </details>

3. Если бомба бьёт башню через интерфейс (`u.TakeDamage(4)`, где `u` — `Unit`), чей `TakeDamage` вызовется?
   <details><summary>Ответ</summary>

   Башни: в интерфейсе лежит `*Tower`, и вызывается метод этого типа, а его `TakeDamage` закрывает метод `Health`. Поэтому
   броня работает и в `hit`, и в `boom`, хотя код `boom` про башни ничего не знает.
   </details>

4. Зачем проверять умение ходить через `u.(Mover)`, а не хранить в юните поле `CanMove bool`?
   <details><summary>Ответ</summary>

   Флаг можно забыть поставить или поставить неправильно: `CanMove: true`, а метода `Move` нет. Проверка по интерфейсу
   опирается на то, что тип **действительно умеет**. Так поступает и стандартная библиотека: например, `fmt` проверяет,
   реализует ли значение `fmt.Stringer`, и только тогда вызывает `String()`.
   </details>
