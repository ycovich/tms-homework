# L7 / Task 14 — nil, any и копии внутри интерфейса

Эта задача — про то, как интерфейс устроен **внутри**, и про самую известную ловушку Go: ошибку, которая равна `nil`, но
при этом `err != nil`. В ней две части: предсказать вывод (как в task_5) и найти и исправить баг в готовой программе.

## Немного теории: что лежит в интерфейсе

На лекции было: переменная интерфейсного типа хранит **пару** — **тип** значения и само значение (точнее, указатель на
его копию):

```
var s Shape = Rect{W: 2, H: 3}

   s:  ┌──────────────┬─────────────────┐
       │ тип: Rect    │ значение: {2 3} │
       └──────────────┴─────────────────┘
```

Из этого следуют четыре правила, на которых держится вся задача.

**1. Интерфейс равен `nil`, только когда пусты обе половины.**

```go
var err error        // тип: нет,   значение: нет  → err == nil  ✔
var p *MyErr         // nil-указатель
err = p              // тип: *MyErr, значение: nil → err != nil  ✘ !
```

Во втором случае значение — nil-указатель, но **тип уже записан**. Интерфейс не пустой: он говорит «внутри лежит
`*MyErr`, просто нулевой». Поэтому `err != nil`, и вызывающий решит, что произошла ошибка.

Отсюда правило: **если ошибки нет, возвращай `nil` явно** (`return nil`), а не переменную-указатель, которая может
оказаться `nil`.

**2. Пустой интерфейс `any` принимает что угодно — и тоже хранит пару.** `var x any` — пустая пара, `x == nil`. А
`x = []int(nil)` кладёт в пару тип `[]int`, и `x == nil` уже `false`. Достать значение обратно можно утверждением типа:
`v, ok := x.(int)`, или проверить несколько типов через `switch x.(type)`. В `switch` по типу есть особая ветка
`case nil`: она срабатывает, только если интерфейс полностью пуст.

**3. Интерфейс хранит копию.** `var s Shape = r` копирует структуру `r` внутрь интерфейса целиком. Потом меняем `r` — `s`
об этом не знает. Положили указатель `&r` — копируется только адрес, и изменения `r` видны через `s`. Вот это уже то же
правило «копируется заголовок, данные общие», что у слайсов и map.

**Ещё одно правило — про nil-указатель без интерфейса.** Метод с получателем-указателем можно вызвать и у
nil-указателя: Go просто передаст `nil` в получатель, и метод сам решает, что с этим делать (так устроен `Len` во
фрагменте 5). Паника случится, только если метод полезет к полям через `nil`.

**4. Два интерфейса равны, когда совпадают обе половины пары:** и тип, и значение. `any(3) == any(3)` — да, а
`any(3) == any(int64(3))` — нет: значения похожи, но типы `int` и `int64` разные.

### Чем nil-указатель в `var _ Payer = (*Card)(nil)` отличается от ловушки

В [task_12](../task_12/task.md) мы тоже клали nil-указатель в интерфейс, и там это было полезно. Разница в цели. В
`var _ Payer = (*Card)(nil)` значение никто не использует: нам важен только **тип**, чтобы компилятор проверил методы.
А в ловушке пара «тип, nil» уходит к вызывающему, и тот сравнивает её с `nil`.

## Зачем эта задача

- Понять, что такое nil-интерфейс, и никогда не попадаться в ловушку «nil-ошибка, которая не nil». Это один из самых
  частых вопросов на собеседованиях по Go и источник настоящих багов в продакшене.
- Научиться пользоваться `any`, утверждением типа и `switch` по типу — и понимать, почему это крайний случай.
- Увидеть, что правило «копия или общее» работает и для интерфейсов, и для map со структурами.

## Проверь себя

Открывай после того, как сделал обе части.

1. Почему в сломанной программе `fmt` печатает `<nil>`, а не падает, хотя `Error()` читает поля через nil-указатель?
   <details><summary>Ответ</summary>

   `e.Field` при `e == nil` действительно вызывает панику. Но `fmt` перехватывает панику внутри `Error()` и `String()`:
   если значение внутри — nil-указатель, он печатает `<nil>`. В своём коде, вне `fmt`, вызов `err.Error()` упал бы с
   `nil pointer dereference`.
   </details>

2. Как функция с результатом `error` может «случайно» вернуть typed nil, даже если ты не пишешь `var verr *ValidationError`?
   <details><summary>Ответ</summary>

   Например, так: `func check() error { return findUser() }`, где `findUser` возвращает `*NotFoundError`, а не `error`.
   Если `findUser` вернул `nil`, он превращается в пару «тип `*NotFoundError`, значение nil». Правило: функции, которые
   сообщают об ошибке, должны возвращать интерфейс `error`, а не конкретный тип-указатель.
   </details>

3. Когда `any` оправдан, а когда лучше свой интерфейс или дженерик?
   <details><summary>Ответ</summary>

   `any` — когда тип **действительно** может быть любым и заранее неизвестен: `fmt.Println`, данные из JSON неизвестной
   формы. Если нужен определённый набор действий — лучше свой интерфейс: компилятор проверит методы. Если код одинаковый
   для разных типов — лучше дженерик: компилятор проверит типы. С `any` ошибку типа увидишь только при запуске, через
   панику в `x.(T)`.
   </details>
