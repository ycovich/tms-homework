# L7 / Task 16 ★ — Своя map (необязательная)

Задача со звёздочкой: её можно не делать. Делай её после task_8.

На лекции мы разобрали, как map устроена внутри: хеш-функция превращает ключ в число, по числу выбирается **бакет**
(корзина), в бакете пары ищутся сравнением, а когда пар становится слишком много, таблица растёт вдвое и пары
**переезжают**. Здесь ты напишешь такую хеш-таблицу сам — упрощённую, но устроенную по тем же принципам. Встроенную
`map` в этой задаче использовать **нельзя**.

## Зачем эта задача

- Понять, почему поиск в map быстрый: смотрим не во все пары, а только в один бакет, где их немного.
- Увидеть коллизии (разные ключи в одном бакете) и рост таблицы своими глазами: команда `stats` показывает, сколько
  пар в каждом бакете.
- Понять, почему у элемента map нет постоянного адреса и почему порядок обхода не совпадает с порядком добавления:
  при росте пары раскладываются по бакетам заново. А разный порядок у двух обходов одной map Go добавляет нарочно —
  каждый обход начинается со случайного места.
- Ещё раз встретить переполнение из task_1: хеш копится в `uint32`, и переполнение здесь нужно специально.

## Устройство

```go
type entry struct {
    key   string
    value int
}

type HashMap struct {
    buckets [][]entry // бакет — слайс пар
    count   int       // сколько всего пар
}
```

**Хеш-функция** — ровно такая (её и проверяют тесты):

```go
func hash(key string) uint32 {
    var h uint32
    for i := 0; i < len(key); i++ { // по БАЙТАМ строки
        h = h*31 + uint32(key[i])
    }
    return h
}
```

Например, `hash("a") = 97`, `hash("ab") = 97·31 + 98 = 3105`, `hash("кот") = 1838056745`. У слова `кот` 6 байтов, и
`h*31` несколько раз переполняет `uint32`. Это нормально: переполнение просто «заворачивает» число.

**Номер бакета** — остаток от деления хеша на число бакетов: `int(hash(key) % uint32(len(buckets)))`.

**Правила:**

1. В начале бакетов **4**, все пустые.
2. `put k v`: найди бакет ключа `k`. Если `k` в нём уже есть — замени значение, число пар не меняется. Иначе добавь пару
   **в конец** бакета, `count++`. Если после этого `count > 2 × (число бакетов)` — таблица растёт.
3. **Рост**: создай вдвое больше пустых бакетов. Затем переложи **все** пары в новые бакеты по новому номеру. Порядок
   перекладывания: старые бакеты от 0 до последнего, внутри бакета — пары от начала к концу. Каждая пара добавляется в
   конец своего нового бакета.
4. `del k`: удали пару из её бакета. Порядок остальных пар в бакете сохраняется, `count--`. Число бакетов при удалении
   не уменьшается.

## Команды

Ввод — команды до конца ввода. Ключ — одно слово без пробелов, значение — целое число. Ввод всегда корректный.

| Команда   | Что печатает                                                                                          |
|-----------|-------------------------------------------------------------------------------------------------------|
| `put K V` | если таблица выросла — `grow <было бакетов> -> <стало бакетов>`, иначе **ничего**                      |
| `get K`   | значение или `нет`                                                                                    |
| `del K`   | `удалено` или `нет`                                                                                   |
| `len`     | число пар                                                                                             |
| `stats`   | `бакетов: <N>, длины: <длина бакета 0> <длина бакета 1> … <длина бакета N-1>`                          |

## Пример

Ввод:

```
put кот 3
put пёс 5
put ёж 1
get пёс
get лис
put кот 4
get кот
stats
put лис 2
put сова 7
put утка 1
put гусь 9
put бобр 6
stats
put конь 8
stats
len
del ёж
del ёж
len
```

Вывод:

```
5
нет
4
бакетов: 4, длины: 0 1 1 1
бакетов: 4, длины: 2 2 1 3
grow 4 -> 8
бакетов: 8, длины: 3 1 0 1 0 1 1 2
9
удалено
нет
8
```

После 8 пар условие роста ещё не выполнено: 8 не больше 2 × 4. Девятая пара (`конь`) даёт 9 > 8 — таблица растёт до
8 бакетов.

## Как решать

- Встроенную `map` не используй нигде в задаче.
- Методы: `Put(key string, value int) bool` (вернёт `true`, если таблица выросла), `Get(key string) (int, bool)`,
  `Delete(key string) bool`, `Len() int`. Плюс конструктор `NewHashMap() *HashMap`, который создаёт 4 пустых бакета.
- Слайсы, `append` и срезы здесь использовать можно: свой слайс ты уже писал в task_10.

## Подсказки

- Удалить элемент `j` из слайса `b` с сохранением порядка: `b = append(b[:j], b[j+1:]...)`. Результат запиши обратно
  в `m.buckets[i]`.
- Чтобы изменить значение пары **внутри** бакета, обращайся по индексу: `m.buckets[i][j].value = v`. Через
  `for _, e := range` получишь копию пары, как в ловушке `range` с лекции.
- Рост удобно сделать так: запомнить `old := m.buckets`, создать новые бакеты и пройти по `old`.

## Проверь себя

1. Почему таблица растёт, когда пар в среднем больше 2 на бакет, а не когда заполнена «вся»?
   <details><summary>Ответ</summary>

   Бакет — слайс, он «заполнен» никогда не бывает. Но чем длиннее бакеты, тем больше сравнений при каждом поиске. Порог
   держит среднюю длину бакета маленькой, и поиск остаётся быстрым при любом числе пар. В настоящей map Go до версии 1.24
   порог был 6,5 пары на бакет из 8 мест.
   </details>

2. Почему после роста пары оказываются в других бакетах?
   <details><summary>Ответ</summary>

   Номер бакета — остаток от деления хеша на число бакетов. Число бакетов изменилось — изменились и остатки. Поэтому в
   Go нельзя взять адрес элемента map (`&m[k]`): после роста пара переедет, и адрес будет указывать не туда.
   </details>

3. Что будет, если хеш-функция плохая, например «длина строки»?
   <details><summary>Ответ</summary>

   Все слова одной длины попадут в один бакет, и поиск превратится в перебор длинного списка — как режим `slice` в task_7.
   Хорошая хеш-функция раскладывает ключи по бакетам равномерно. От неё зависит вся скорость map.
   </details>
