# L7 / Task 12 — Оплата

У покупателя несколько способов оплаты: наличные, карта, электронный кошелёк. Магазин пробует их **по очереди** в
порядке, который задал покупатель. Если способ отказал, магазин объясняет почему и переходит к следующему. Первый
сработавший способ платит.

Магазину неважно, чем именно платят: ему нужно только, чтобы способ умел **заплатить**. Это и есть интерфейс:

```go
type Payer interface {
    Pay(amount int) error
}
```

## Зачем эта задача

- Написать свой интерфейс и три типа, которые его реализуют, и увидеть **полиморфизм**: один цикл
  `for _, p := range payers { p.Pay(amount) }` вызывает три разных метода.
- Разобраться с ошибками как интерфейсом: своя **сигнальная** ошибка (`ErrInsufficient`), свой **тип** ошибки
  (`*LimitError`), обёртка через `%w` и поиск по цепочке через `errors.Is` и `errors.As`.
- Освоить приём `var _ Payer = (*Card)(nil)`: компилятор сам проверит, что тип реализует интерфейс.

Где это в жизни: так устроены платёжные системы, отправка уведомлений (SMS, e-mail, push), хранилища (диск, облако,
память). Код, который «платит» или «отправляет», знает только интерфейс, а новый способ добавляется без его изменения.

## Способы оплаты

Деньги — целые числа (рубли). Каждый способ — структура и метод `Pay` с получателем-указателем: он **меняет** остаток.

| Тип       | Поля                                                                                   |
|-----------|----------------------------------------------------------------------------------------|
| `Cash`    | `Name string`, `Amount int` — сколько наличных                                         |
| `Card`    | `Name string`, `Limit int` — наибольший разовый платёж, `Balance int` — деньги на карте |
| `Wallet`  | `Name string`, `Balance int`                                                           |

Правила `Pay(amount)` проверяются сверху вниз, первое сработавшее побеждает.

**`(c *Cash) Pay`**

1. `amount` не делится на 10 — ошибка `наличные <Name>: нужна мелочь`. Это обычная ошибка, без `%w`.
2. `amount > Amount` — ошибка `наличные <Name>: ` + обёрнутая `ErrInsufficient`.
3. Иначе `Amount -= amount`, ошибки нет.

**`(c *Card) Pay`**

1. `amount > Limit` — ошибка `карта <Name>: ` + обёрнутая `&LimitError{Limit: …, Amount: …}`.
2. `amount > Balance` — ошибка `карта <Name>: ` + обёрнутая `ErrInsufficient`.
3. Иначе `Balance -= amount`, ошибки нет.

**`(w *Wallet) Pay`**

1. `amount > Balance` — ошибка `кошелёк <Name>: ` + обёрнутая `ErrInsufficient`.
2. Иначе `Balance -= amount`, ошибки нет.

Ошибки. Напомним с лекции: `error` — обычный интерфейс с одним методом `Error() string`. Любой тип с таким методом
и есть ошибка, как любой тип с `String()` — это `fmt.Stringer`.

```go
// сигнальная ошибка: «не хватает денег»
var ErrInsufficient = errors.New("недостаточно средств")

// тип ошибки: платёж больше лимита карты
type LimitError struct {
    Limit  int
    Amount int
}

// получатель — указатель: ошибку реализует *LimitError
func (e *LimitError) Error() string // возвращает "лимит <Limit>, платёж <Amount>"
```

«Обёрнутая» значит созданная через `fmt.Errorf` с `%w`, например
`fmt.Errorf("кошелёк %s: %w", w.Name, ErrInsufficient)`. Её текст — `кошелёк Qiwi: недостаточно средств`. Для карты оборачивай именно **указатель**:
`fmt.Errorf("карта %s: %w", c.Name, &LimitError{Limit: c.Limit, Amount: amount})`. Если обернуть значение
`LimitError{…}` без `&`, `errors.As` с переменной типа `*LimitError` его не найдёт.

Каждый тип реализует ещё и `fmt.Stringer` — метод `String() string`, который описывает остаток:

| Тип       | `String()`                              |
|-----------|-----------------------------------------|
| `*Cash`   | `наличные <Name>: <Amount>`             |
| `*Card`   | `карта <Name>: <Balance> (лимит <Limit>)` |
| `*Wallet` | `кошелёк <Name>: <Balance>`             |

## Ввод

1. Число `n` — сколько способов оплаты, 1 ≤ `n` ≤ 10.
2. `n` строк, по способу в каждой, **в порядке приоритета**:
   - `cash <имя> <сумма>`
   - `card <имя> <лимит> <баланс>`
   - `wallet <имя> <баланс>`
3. Дальше до конца ввода — платежи: `pay <сумма>`, сумма — целое число больше нуля. Платежей может не быть совсем.

Имена — одно слово, все числа целые и неотрицательные. Ввод всегда корректный.

## Вывод

Для каждого платежа:

1. строка `платёж <сумма>`;
2. для каждого способа, который пробовали, по порядку — **одна** строка с двумя пробелами в начале:
   - отказ: `  отказ (<вид>): <текст ошибки>`;
   - успех: `  оплачено: <String() этого способа после оплаты>`. После успеха остальные способы не пробуют;
3. если не сработал ни один способ — после всех отказов строка `  не удалось оплатить`.

`<вид>` ошибки определяется **по цепочке ошибок**, а не по тексту:

| Условие                                       | `<вид>`     |
|-----------------------------------------------|-------------|
| `errors.As` нашёл в цепочке `*LimitError`     | `лимит`     |
| иначе: `errors.Is(err, ErrInsufficient)`      | `нет денег` |
| иначе                                         | `другое`    |

После всех платежей — строка `---` и `String()` каждого способа в порядке ввода, по одному на строку.

## Как решать

- Способы оплаты храни в одном слайсе `[]Payer` и перебирай его. В цикле оплаты не должно быть проверок «какой это тип»:
  только вызов `p.Pay(amount)`.
- Вид ошибки определяй функцией `kind(err error) string` через `errors.As` и `errors.Is`. Сравнивать текст ошибки
  (`strings.Contains(err.Error(), …)`) или сами ошибки через `==` нельзя.
- `String()` способа печатай через `fmt.Println(p)` или `%v`: `fmt` сам вызовет `String()`, потому что тип реализует
  `fmt.Stringer`. Хотя в переменной `p` лежит `Payer`, `fmt` смотрит на тип **внутри** интерфейса.
- **Обязательно** добавь в программу проверки при компиляции:

  ```go
  var (
      _ Payer        = (*Card)(nil)
      _ Payer        = (*Wallet)(nil)
      _ Payer        = (*Cash)(nil)
      _ error        = (*LimitError)(nil)
      _ fmt.Stringer = (*Card)(nil)
      _ fmt.Stringer = (*Wallet)(nil)
      _ fmt.Stringer = (*Cash)(nil)
  )
  ```

### Что такое `var _ Payer = (*Card)(nil)`

Разберём по частям:

- `(*Card)(nil)` — преобразование `nil` в тип `*Card`: nil-указатель на `Card`. Памяти под `Card` не выделяется.
- `var _ Payer = …` — объявить переменную типа `Payer` и положить туда этот указатель. Имя `_` значит «переменная не
  нужна», её никто не использует.

Зачем это? Чтобы положить `*Card` в переменную типа `Payer`, у `*Card` должны быть все методы `Payer`. Если ты опечатался
в имени метода (`Pya`), забыл его или поставил получатель-значение не там, где нужно, программа **не скомпилируется**,
и ошибка покажет на эту строку. Без такой проверки ошибка всплыла бы где-то далеко, в месте использования, а то и не
всплыла бы совсем: для `fmt.Stringer` Go молча напечатает поля структуры вместо `String()`. Это **рамка**, которую ты
задаёшь типу: «этот тип обязан быть `Payer`», и компилятор её охраняет.

## Подсказки

- `errors.As` нужен адрес переменной-указателя: `var le *LimitError` и `errors.As(err, &le)`. Найдя ошибку, он кладёт её в
  `le`, и дальше можно читать `le.Limit`.
- Проверь `As` раньше, чем `Is`: так требует таблица видов.
- Ошибку «нужна мелочь» создавай без `%w`: `fmt.Errorf("наличные %s: нужна мелочь", c.Name)`. Она не оборачивает
  `ErrInsufficient`, поэтому её вид — `другое`.

## Проверь себя

1. Почему `err == ErrInsufficient` вернёт `false`, хотя текст ошибки содержит «недостаточно средств»?
   <details><summary>Ответ</summary>

   `fmt.Errorf("кошелёк %s: %w", …)` создаёт **новую** ошибку, а `ErrInsufficient` хранится у неё внутри. `==` сравнивает
   только верхний слой. `errors.Is` разворачивает цепочку слой за слоем и находит `ErrInsufficient` внутри.
   </details>

2. Чем `errors.Is` отличается от `errors.As`?
   <details><summary>Ответ</summary>

   **Is ищет конкретное значение** («это та самая ошибка `ErrInsufficient`?»). **As ищет тип** («есть ли в цепочке
   какая-нибудь `*LimitError`?») и достаёт её, чтобы прочитать поля, например лимит. Сигнальная ошибка — когда достаточно
   знать «что случилось». Тип ошибки — когда нужны подробности.
   </details>

3. Что изменится в программе, если добавить четвёртый способ оплаты, например `Bonus` (бонусные баллы)?
   <details><summary>Ответ</summary>

   Появится новый тип с методами `Pay` и `String`, строчка `var _ Payer = (*Bonus)(nil)` и одна ветка при чтении ввода.
   Цикл оплаты, функция `kind` и вывод итогов не изменятся: они работают с `Payer` и `error`, а не с конкретными типами.
   </details>
