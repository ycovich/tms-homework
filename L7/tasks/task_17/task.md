# L7 / Task 17 ★ — Поиск: считаем шаги (необязательная)

Задача со звёздочкой: её можно не делать. Перед ней прочитай про O-нотацию — ссылки в [L7/README.md](../../README.md).

Есть отсортированный по возрастанию список чисел. Нужно находить в нём числа двумя способами и считать, сколько шагов
сделал каждый:

- **Линейный поиск** идёт по порядку с начала и сравнивает каждый элемент с искомым.
- **Бинарный поиск** смотрит в середину. Если там число меньше искомого — искомое может быть только правее, и левая
  половина отбрасывается целиком. Если больше — отбрасывается правая. Как в игре «угадай число от 1 до 100»: «больше»,
  «меньше» — и за 7 вопросов ответ найден.

## Зачем эта задача

- Увидеть разницу O(n) и O(log n) в цифрах. Для 10 чисел разница небольшая, для миллиона — 1 000 000 шагов против 20.
- Понять, что бинарный поиск работает **только** на отсортированных данных. Это цена его скорости: данные надо держать
  в порядке.

## Как считать шаги

**Линейный поиск.** Идём по индексам 0, 1, 2, … Каждое сравнение элемента с искомым — один шаг. Нашли — останавливаемся.
Не нашли — шагов столько, сколько элементов.

**Бинарный поиск** — ровно по этому алгоритму:

```
lo = 0, hi = длина - 1
пока lo <= hi:
    mid = lo + (hi - lo) / 2      ← целое деление
    шаг++                         ← один шаг = один взгляд на s[mid]
    если s[mid] == x: нашли, индекс mid
    если s[mid] < x:  lo = mid + 1
    иначе:            hi = mid - 1
не нашли: индекс -1
```

## Ввод

1. Первая строка — от 1 до 5 000 целых чисел через пробел, **строго по возрастанию** (без повторов). Каждое число — от −1 000 000 до 1 000 000.
2. Дальше до конца ввода — искомые числа, по одному на строку. Их может не быть совсем.

Ввод всегда корректный.

## Вывод

Для каждого искомого числа `x`:

```
<x>: линейный <индекс> за <шаги>, бинарный <индекс> за <шаги>
```

Индекс — позиция в списке с 0, или `-1`, если числа нет. В конце:

```
всего шагов: линейный <сумма>, бинарный <сумма>
```

## Пример

Ввод:

```
2 5 8 12 16 23 38 56 72 91
23
2
91
7
```

Вывод:

```
23: линейный 5 за 6, бинарный 5 за 3
2: линейный 0 за 1, бинарный 0 за 3
91: линейный 9 за 10, бинарный 9 за 4
7: линейный -1 за 10, бинарный -1 за 3
всего шагов: линейный 27, бинарный 13
```

Бинарный поиск `23`: `lo=0, hi=9` → `mid=4` (16 < 23) → `lo=5` → `mid=7` (56 > 23) → `hi=6` → `mid=5` (23) — нашли за 3 шага.
Число `2` линейный нашёл сразу, а бинарный потратил 3 шага. На маленьких данных и для элементов в начале простой
перебор бывает не хуже.

## Как решать

- Две функции: `linear(s []int, x int) (int, int)` и `binary(s []int, x int) (int, int)`. Обе возвращают индекс и число шагов.
- Пиши поиск сам: `slices.Index`, `slices.BinarySearch` и похожие не используй.
- Рекурсия здесь не нужна, хватит цикла.

## Подсказки

- `lo + (hi-lo)/2` вместо `(lo+hi)/2` — защита от переполнения, когда `lo + hi` больше максимального `int`. Для наших
  размеров это не важно, но так принято писать.

## Проверь себя

1. Сколько шагов бинарному поиску нужно в худшем случае на 1 000 000 чисел?
   <details><summary>Ответ</summary>

   Около 20: каждый шаг делит область поиска пополам, а 2²⁰ ≈ 1 000 000. Это и есть O(log n). Линейному в худшем случае
   нужен миллион шагов, O(n).
   </details>

2. Если список не отсортирован, что вернёт бинарный поиск?
   <details><summary>Ответ</summary>

   Что угодно: он может не найти число, которое в списке есть. Он отбрасывает половину, полагаясь на порядок, а порядка нет.
   Поэтому бинарный поиск выбирают, когда данные **много раз ищут и редко меняют**: один раз отсортировать, потом искать
   быстро.
   </details>
