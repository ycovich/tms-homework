# L8 — ДЗ к уроку 8: горутины и каналы

ДЗ из трёх задач и одной необязательной со ★. Цель — **своими руками** запустить горутины, научиться их дожидаться и
передавать результаты через каналы. Рассчитывай примерно на 4–5 часов: кода немного, но много нового. `select` и
таймеры здесь не понадобятся, на 9-й лекции продолжим асинхронную модель Go.

Делай задачи **по порядку**: каждая следующая опирается на предыдущую.

Устроено как в L7: в каждом `task.md` есть «Зачем эта задача», «Как решать» и «Проверь себя» с ответами под спойлером.
Новое здесь — заметки **«Под капотом»**. Они коротко объясняют, как устроены процессы, потоки и горутины. Для решения
они не нужны, но объясняют, *почему* программа ведёт себя именно так. Не пропускай их: в этом половина пользы от ДЗ.

## Задачи

|--------------------------------------------------------|----------------------------------------------------------------------------------------------------|
| [task_1 — Десять тысяч кастрюль](tasks/task_1/task.md) | `go func(){}()`, как дождаться горутин через канал; ядра, процесс, потоки ОС и горутины в цифрах   |

Задачи выстроены по одной линии. В task_1 горутины независимы, и `main` просто ждёт, пока закончат все. В task_2
горутины ждут **друг друга**: суп не начнёшь, пока не закипела вода. В task_3 между горутинами идёт целый поток
значений, и сколько их будет, заранее неизвестно.

Задача со ★ необязательная: без неё ДЗ засчитывается полностью.

## Модель кухни

Все задачи — про кухню: там конкурентность видна без всякого компьютера. Поставил воду, и пока она греется, режешь
овощи. Ждать у кастрюли, пока она закипит, никто не станет.

Главное различие, которое понадобится во всех задачах:

- **Ожидание.** Вода закипает сама: плита греет, а руки свободны. Можно поставить хоть пять кастрюль. В программе это
  ожидание сети, диска, базы данных, у нас его имитирует `time.Sleep`.
- **Работа руками.** Нарезать лук можно, только держа нож: руки заняты всё время. Двух луковиц одновременно одними
  руками не нарежешь. В программе это вычисления: они всё время занимают ядро процессора.

Для заметок «Под капотом» представь ресторан. На кухне несколько рабочих мест — плита и стол. За каждым местом в каждый
момент стоит один повар. Поваров больше, чем мест, и кого к какому месту поставить и надолго ли, решает шеф. Кухня ведёт
несколько заказов сразу, например «Свадьба» и «Детский сад». У каждого заказа свои повара и свои закрытые коробки с
продуктами: испортился один заказ — второй не пострадал. Задачи поварам заказа раздаёт старший по заказу: пока тесто
подходит, повар чистит овощи.

| В ресторане                                                | В компьютере                              |
|------------------------------------------------------------|-------------------------------------------|
| Ресторан                                                   | компьютер                                 |
| Кухня                                                      | процессор                                 |
| Рабочее место: плита, стол и т. п.                         | ядро процессора                           |
| Шеф: кого из поваров к какому месту поставить и надолго ли | планировщик ОС                            |
| Заказ «Свадьба» со своими коробками продуктов              | процесс и его память                      |
| Коробки другого заказа                                     | память другого процесса: тебе её не видно |
| Повар, который работает над заказом                        | поток ОС                                  |
| Задача повара: почистить, нарезать, сварить                | горутина                                  |
| Старший по заказу раздаёт задачи поварам заказа            | планировщик Go                            |
| Крик «Бульон готов!», передача тарелки из рук в руки       | канал                                     |
| Два повара солят один суп, не договорившись                | гонка данных                              |

Работу делает поток — повар у рабочего места, то есть ядра. Процесс — заказ — сам ничего не режет: это коробки с
продуктами и повара, которые над ним работают. Горутина — одна задача в списке. Повар делает задачи **по очереди**:
пока суп варится, он режет лук. Одновременно идут только задачи разных поваров на разных рабочих местах.

## Зачем всё это

- **Программа постоянно чего-то ждёт:** ответа базы, сети, диска. Пока одно дело ждёт, другое может идти. Это и дают
  горутины: сервер на Go держит тысячи запросов сразу, потому что почти все они в этот момент ждут.
- **Горутина дешёвая, поток ОС — дорогой.** Тысячи горутин работают на нескольких потоках. В task_1 ты сам посчитаешь,
  сколько потоков понадобилось на 10 000 горутин.
- **Горутины надо согласовывать:** дождаться, начать следующий шаг, когда готовы предыдущие, передать результат дальше.
  Для этого нужны каналы. Если писать в общую переменную, будет гонка данных.
- **Горутины не волшебные.** Ожидание они ускоряют почти бесконечно, а вычисления — не больше, чем позволяет число ядер.
  В task_1 видно почему: потоков ОС у Go примерно столько, сколько ядер.

## Что можно использовать

Всё, что было на уроках 5–8. `select` и таймеры использовать можно, но в этих задачах они не нужны.

Нельзя:

- пакеты `sync` (`WaitGroup`, `Mutex`), `sync/atomic` и `context`: их разберём на следующих уроках. Здесь цель —
  научиться обходиться каналами;
- `time.Sleep`, чтобы **дождаться** горутин. На лекции это был костыль: сколько ждать, заранее неизвестно. `Sleep`
  можно только там, где он **изображает работу** и об этом сказано в условии;
- внешние библиотеки.

## Как читать ввод

Как в L7: сканер создаём один раз и читаем до конца ввода.

```go
in := bufio.NewScanner(os.Stdin)
for in.Scan() { // false — строки кончились
	f := strings.Fields(in.Text())
	// ...
}
```

Если первая строка особая, прочитай её отдельным `in.Scan()` **до** цикла. Конец ввода в терминале — `Ctrl+D` (macOS,
Linux, Git Bash) или `Ctrl+Z`, затем Enter (PowerShell и cmd).

На Windows подавай файл с вводом через Git Bash (`go run . < in.txt`) или cmd (`cmd /c "go run . < in.txt"`). В
PowerShell при передаче через `|` русские буквы могут превратиться в `????`, и правильная программа выдаст ерунду.

## Проверка на гонки: `-race`

С лекции: гонку данных глазами не поймать, поэтому программу запускают с флагом `-race`:

```bash
go run -race .
```

Если гонок нет, программа просто работает как обычно. Если есть — Go напечатает `WARNING: DATA RACE`. Прогони так
task_2, task_3 и task_4 перед сдачей. Время замеряй без `-race`: с ним программа работает в несколько раз медленнее.

На Windows `-race` работает только с установленным компилятором C (gcc). Если флаг не запускается, пропусти этот шаг:
гонки проверит преподаватель.

## Как проверяется

1. Задачи 2, 3 и 4 запускаются на закрытом наборе тестов, вывод сравнивается с правильным **символ в символ**. Время на
   один тест ограничено — 5 секунд. Во всех трёх есть тесты «на время»: решение, которое выполняет шаги по очереди, в
   них не уложится. Решение без горутин и каналов не засчитывается, даже если тесты прошли: код читает преподаватель.
2. В task_1 файл `answers.txt` сверяется автоматически. Число ошибок в предсказаниях на зачёт не влияет. `README.md`
   читает преподаватель.
3. Код читает преподаватель. Требования из раздела «Как решать» обязательны: нет `Sleep` для ожидания горутин, нет
   `sync`, нет гонок данных.
