# L11 / Task 1 — Сервис каталога

## Что мы делаем

Магазину нужен сервис каталога: по сети можно добавить товар и посмотреть список. Мы пишем его на `net/http` и сразу
раскладываем по packages:

| Package      | За что отвечает                                             | Знает о каталоге? |
|--------------|-------------------------------------------------------------|-------------------|
| `logging`    | создаёт логгер нужного формата                              | нет               |
| `middleware` | две обёртки вокруг обработчика: номер запроса и лог запроса | нет               |
| `server`     | запускает сервер и аккуратно останавливает его              | нет               |
| `catalog`    | сам каталог: товары и маршруты                              | да                |
| `main.go`    | собирает всё вместе                                         | —                 |

Как проходит запрос:

```
curl ──▶ server.Run(ctx, addr, …)        ← порт, timeout, остановка по Ctrl+C
            └─▶ RequestID ──▶ Logging ──▶ [RequireToken ★] ──▶ catalog: GET/POST /products
                                 └─▶ log = logging.New(os.Stdout, LOG_FORMAT)
```

Запрос проходит обёртки снаружи внутрь, ответ — обратно. Что получится в конце: `go run .` запускает сервер, `curl`
добавляет и показывает товары, у каждого ответа есть заголовок `X-Request-ID`, в консоли на каждый запрос появляется
строка лога, а Ctrl+C останавливает сервер, не обрывая запросы.

Первые три package ничего не знают о каталоге **специально**: в L12 мы подключим их к другому приложению, DataShifter, и
не будем писать заново. На место `catalog` там встанет другой маршрут. Поэтому имена packages, функций и их параметры
менять нельзя, они уже написаны в заготовках.

Закрытые тесты вызывают функции этих packages напрямую. Рассчитывай примерно на 4 часа. Только стандартная библиотека
Go.

## С чего начать

1. Создай папку `L11/task_1` и в ней модуль: `go mod init shop`. Имя модуля должно быть именно `shop`.
2. Скопируй в неё папки-заготовки `logging`, `middleware`, `server`, `catalog`. В каждой функции тело пустое
   (`// TODO`). Твоя работа — заменить `TODO` настоящим кодом.
3. Сразу создай `main.go` с `package main` и пустой `func main() {}`: без него корень модуля не соберётся, и
   `go build ./...` будет ругаться. Наполнишь его в шаге 5.
4. Идём по шагам **от простого к сложному**. После каждого шага код должен собираться: `go build ./...`.

## Базовое задание

### Шаг 1. Package `logging`

```go
func New(w io.Writer, format string) *slog.Logger
```

Возвращает логгер, который пишет в `w`. Если `format` равен `"json"`, строки лога — JSON. При любом другом значении (в
том числе пустом) — обычный текст.

```
json:  {"time":"2026-11-02T19:00:00+03:00","level":"INFO","msg":"привет"}
text:  time=2026-11-02T19:00:00.000+03:00 level=INFO msg=привет
```

Логгер собирается одной строкой: `slog.New(slog.NewJSONHandler(w, nil))` для JSON (слайд «Логи», L11) или
`slog.New(slog.NewTextHandler(w, nil))` для текста — тот же логгер, только строки пишутся парами `ключ=значение`.

Зачем второй параметр `io.Writer`, а не просто `os.Stdout`: в L12 лог пойдёт сразу и в консоль, и в файл.

### Шаг 2. Package `catalog`

Каталог товаров в памяти. Метод `Handler()` каталога (`NewStore().Handler()`) возвращает `http.Handler` с тремя
маршрутами. Каждый вызов `NewStore()` создаёт отдельный пустой каталог.

Товар — struct `Product` из заготовки: поля как в L10, но без `Note`. Добавь теги `json`, как в L10. `Validate` тоже
возьми из L10, но **без проверки `id`**: в `POST` номера ещё нет, его выдаёт сервер. Остаются две проверки — сначала
название, потом цена — с теми же текстами ошибок. Товар в JSON выглядит так, поля именно в таком порядке:

```
{"id":1,"name":"Чайник","price":2990,"in_stock":true}
```

| Запрос               | Ответ                                                                                         |
|----------------------|-----------------------------------------------------------------------------------------------|
| `GET /products`      | `200` и список всех товаров по возрастанию `id`. Если каталог пуст, то `[]`                   |
| `GET /products/{id}` | `200` и один товар                                                                            |
| `POST /products`     | в теле `{"name":"Чайник","price":2990,"in_stock":true}`; ответ `201` и созданный товар с `id` |

`id` выдаёт сервер: 1, 2, 3… по порядку добавления. Если клиент прислал `id` в теле, он игнорируется. Если `POST`
закончился ошибкой, номер не тратится.

Ошибки — всегда JSON `{"error":"<текст>"}`:

| Когда                                                               | Код   | Текст                           |
|---------------------------------------------------------------------|-------|---------------------------------|
| в `POST` тело — не JSON или поле не того типа (`"price": "дорого"`) | `400` | `неверный JSON`                 |
| в `POST` пустое название (или одни пробелы)                         | `400` | `название не может быть пустым` |
| в `POST` цена не больше нуля                                        | `400` | `цена должна быть больше нуля`  |
| в пути `{id}` — не число                                            | `400` | `id должен быть числом`         |
| товара с таким `id` нет                                             | `404` | `товар не найден`               |

В `POST` проверки идут по порядку: сначала JSON, потом название, потом цена. Маршруты регистрируй с методом в шаблоне,
как на слайде «Маршруты» (L11): `"GET /products"`, `"GET /products/{id}"`, `"POST /products"`. Тогда на неизвестный
адрес Go сам ответит `404 page not found`, а на другой метод — `405 Method Not Allowed`: писать для них ничего не нужно.

Хранилище — struct `Store`. Он и `NewStore()` уже написаны в заготовке, дописывать их не нужно. В `Store` три поля:
`items` (`map` «номер → товар»), `nextID` (номер, который получит следующий добавленный товар) и `mu` (mutex).
`NewStore()` создаёт пустой `map` и кладёт в `nextID` единицу, потому что первый товар должен получить `id` 1. В `POST`
ты берёшь `id := s.nextID`, сохраняешь товар под этим номером и увеличиваешь `s.nextID` на единицу.

Все запросы приходят в разных goroutines, а каталог один на всех. Поэтому каждое обращение к `items` и `nextID` —
чтение, запись, удаление, добавление — делай между `s.mu.Lock()` и `s.mu.Unlock()` (`defer s.mu.Unlock()` сразу после
`Lock`).

Каркас, с которого удобно начать. Обработчики — методы `*Store` с обычной сигнатурой
`func (s *Store) list(w http.ResponseWriter, r *http.Request)`:

```go
func (s *Store) Handler() http.Handler {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /products", s.list)
    mux.HandleFunc("GET /products/{id}", s.get)
    mux.HandleFunc("POST /products", s.create)
    return mux
}
```

Ответы и ошибки удобно слать двумя маленькими функциями: `writeJSON(w, status, v)` и `writeError(w, status, msg)`. Они
разобраны на слайдах «Отвечаем JSON» и «Ошибки в обработчике» (L11); перепиши их в `catalog`.

### Шаг 3. Package `middleware`

Middleware — функция, которая получает обработчик и возвращает новый, «обёрнутый». Новый делает что-то до и после
старого. Обе наши функции имеют одну форму: получили `next`, вернули `http.HandlerFunc`, который вызывает
`next.ServeHTTP(w, r)`.

```go
func RequestID(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // сделать что-то до next
        next.ServeHTTP(w, r)
        // сделать что-то после next
    })
}
```

**`RequestID(next http.Handler) http.Handler`.** Перед вызовом `next` ставит в ответ заголовок `X-Request-ID` с номером
запроса: `1`, `2`, `3`… Номера идут подряд с момента запуска программы, у каждого запроса свой. Запросы приходят из
разных goroutines, поэтому счётчик — `atomic.Int64`: объяви его на уровне package (`var requests atomic.Int64`), а
`requests.Add(1)` прибавит единицу и вернёт новое значение. Число в строку переводит `strconv.FormatInt(n, 10)`.

**`Logging(log *slog.Logger, next http.Handler) http.Handler`.** Вызывает `next`, а **после** него пишет в `log` одну
строку с четырьмя атрибутами:

| Атрибут    | Что в нём                                                                 |
|------------|---------------------------------------------------------------------------|
| `method`   | метод запроса: `r.Method`                                                 |
| `path`     | путь без параметров после `?`: `r.URL.Path`                               |
| `status`   | код ответа числом                                                         |
| `duration` | сколько заняла обработка: `time.Since(start)`, где `start` взят до `next` |

Текст сообщения придумай сам, например `запрос`. Строка в логе будет такой:

```
time=… level=INFO msg=запрос method=POST path=/products status=201 duration=134µs
```

Код ответа `ResponseWriter` не хранит, поэтому мы взяли готовый struct `statusRecorder` из файла `recorder.go`. Тебе
остаётся правильно его использовать:

1. Перед вызовом `next` создай `rec := &statusRecorder{ResponseWriter: w, status: http.StatusOK}`.
2. Передай в `next.ServeHTTP` не `w`, а `rec`.
3. После вызова бери код из `rec.status`.

Ответ клиенту `Logging` менять не должен. Если обработчик не задавал код, это `200`: так и записано в `rec` по
умолчанию.

### Шаг 4. Package `server`

```go
func Run(ctx context.Context, addr string, h http.Handler, log *slog.Logger) error
```

Запускает `h` на адресе `addr` и работает, пока не отменён `ctx`. Нужно, чтобы:

- сервер был создан через `&http.Server{…}` с timeout `ReadTimeout: 5 * time.Second` и `WriteTimeout: 10 * time.Second`,
  как на слайде «Тайм-ауты сервера и остановка по Ctrl+C» (L11);
- в лог попали три сообщения: сервер запущен (с адресом), остановка началась, сервер остановлен. Тексты придумай сам.
  «Сервер запущен» пишется до того, как `ListenAndServe` займёт порт: если порт занят, сразу следом придёт ошибка, и
  это нормально;
- когда `ctx` отменили, сервер перестал принимать новые соединения, но запросы, которые уже выполняются, дошли до конца,
  не дольше 10 секунд (`srv.Shutdown`);
- при нормальной остановке `Run` вернула `nil`; если сервер не запустился (например, порт занят), вернула эту ошибку.

План: `ListenAndServe` запусти в отдельной goroutine, а в основной подожди одно из двух: ошибку оттуда или `ctx.Done()`.
Ошибка `http.ErrServerClosed` — не ошибка, а признак того, что сервер остановили как надо. `Run` ничего не знает о
каталоге: она получает любой `http.Handler`.

```go
srv := &http.Server{Addr: addr, Handler: h /* + timeout */}
errc := make(chan error, 1)
go func() { errc <- srv.ListenAndServe() }()
select {
case err := <-errc:
    return err // сервер не запустился
case <-ctx.Done():
}
// сюда попадаем после отмены: останови сервер через srv.Shutdown(…) с контекстом на 10 секунд
```

**Контекст для `Shutdown` создавай от `context.Background()`, а не от `ctx`**, как на слайде:
`context.WithTimeout(context.Background(), 10*time.Second)`. `ctx` к этому моменту уже отменён, и контекст, сделанный из
него, тоже отменён сразу: `Shutdown` вернёт `context canceled`, не дождавшись запросов. `Run` должна вернуться только
после того, как `Shutdown` дождался выполняющихся запросов: иначе `main` завершится и оборвёт их.

### Шаг 5. `main.go`

Собери приложение:

1. логгер: `logging.New(os.Stdout, os.Getenv("LOG_FORMAT"))`;
2. адрес из переменной `ADDR`; если она пустая — `":8080"`;
3. обработчик, обёртки вкладываются друг в друга:

   ```go
   handler := middleware.RequestID(middleware.Logging(log, catalog.NewStore().Handler()))
   ```

   `RequestID` стоит снаружи, чтобы номер был у каждого ответа;
4. контекст, который отменяется по Ctrl+C и по сигналу `SIGTERM` (его посылают `kill` и Docker при остановке):
   `ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)` и `defer stop()` — как на
   слайде L11, только с ещё одним сигналом;
5. `server.Run(ctx, addr, handler, log)`. Если вернулась ошибка, запиши её в лог уровнем `ERROR` и завершись с кодом
   `1`.

Запусти и проверь руками:

```bash
LOG_FORMAT=json go run .
```

В другом терминале:

```bash
curl -i -X POST localhost:8080/products -d '{"name":"Чайник","price":2990,"in_stock":true}'
curl -i localhost:8080/products
curl -i localhost:8080/products/abc
```

В первом ответе должны быть код `201`, заголовок `X-Request-Id: 1` (так Go пишет `X-Request-ID`; регистр в именах
заголовков не важен) и созданный товар. В терминале сервера для каждого запроса появится строка лога. Нажми Ctrl+C: в
логе появятся твои сообщения об остановке.

## Подсказки

- **Теги `json` обязательны:** без них поле `InStock` попадёт в JSON как `InStock`, а не `in_stock` (L10).
- **Тело запроса:** `json.NewDecoder(r.Body).Decode(&p)`; ошибка здесь — это `400 неверный JSON`.
- **Номер из пути:** `r.PathValue("id")`, в число — `strconv.Atoi`. Вынеси это в маленькую функцию, чтобы не писать
  дважды.
- **Список по возрастанию `id`:** собери ключи `map` в slice и отсортируй `slices.Sort`. `map` порядок не хранит.
- **Пустой список — `[]`, а не `null`:** создавай slice через `make([]Product, 0, …)` (L10).
- **Заголовки ставь до записи тела:** `w.Header().Set(…)` и `w.WriteHeader(…)` должны идти раньше `Write` (L11).
- **Вспомогательные функции ответа** (`writeJSON`, `writeError`) нужны каталогу. Не делай их общими с `middleware`,
  пусть каждый package живёт сам по себе.
- **Тест остановки** запускает настоящий сервер на свободном порту, шлёт запрос, который выполняется около полсекунды, и
  отменяет контекст посреди него. Ответ должен всё равно прийти полностью.

Дерево репозитория, то, что проверяют тесты, и способ сдачи смотри в [README](../../README.md).

## Зачем эта задача

- **Каталог один на все запросы, а запросы идут в разных goroutines (L11).** Поэтому его защищает `Mutex`.
- **Middleware — обёртка вокруг обработчика (L11).** Номер запроса и лог нужны каждому маршруту. Вместо того чтобы
  писать их в каждом обработчике, оборачиваем один раз.
- **Packages не знают о каталоге, и поэтому их можно взять в другое приложение.** Это и называется переиспользуемым
  кодом.
- **Настройки приходят из переменных окружения (L11).** Формат лога и адрес выбирают при запуске, не правя код.
- **`Shutdown` дожидается выполняющихся запросов (L11).** Обычное завершение по Ctrl+C их обрывает.

## Проверь себя

1. Почему `logging`, `middleware` и `server` не должны знать о каталоге?
   <details><summary>Ответ</summary>

   Если в `middleware` появится `import "shop/catalog"`, то взять его в другое приложение можно будет только вместе с
   каталогом. А если package принимает только то, что есть у любого сервера (`http.Handler`, `io.Writer`,
   `*slog.Logger`), его можно подключить куда угодно. В L12 это и произойдёт: DataShifter возьмёт логгер, middleware и
   запуск сервера, а каталога у него не будет.

   Зачем отдельный package ради пяти строк `logging.New`? В нём одно решение: как выглядит лог и как его формат
   выбирают через `LOG_FORMAT`. Пока это решение в одном месте, каталог и DataShifter пишут лог одинаково, а менять
   формат придётся только в одном файле.
   </details>

2. Почти все запросы в закрытых тестах идут по одному. Зачем тогда mutex в каталоге?
   <details><summary>Ответ</summary>

   Настоящие клиенты шлют запросы одновременно, и `net/http` выполняет каждый в своей goroutine. Две goroutines, которые
   одновременно пишут в один `map`, роняют программу с ошибкой `concurrent map writes`. Последний тест как раз запускает
   100 параллельных запросов. mutex нужен и для номера следующего товара: без него два запроса получат один `id`.
   </details>

3. Зачем нужен struct `statusRecorder`? Нельзя просто взять код ответа у `ResponseWriter`?
   <details><summary>Ответ</summary>

   У `http.ResponseWriter` нет метода «какой код был отправлен»: обработчик вызывает `WriteHeader`, и код уходит
   клиенту, а interface его не хранит. `statusRecorder` встраивает настоящий `ResponseWriter` и перехватывает один
   метод: запоминает код и передаёт вызов дальше. Остальное работает как раньше, поэтому клиент ничего не замечает.
   </details>

4. Чем `Shutdown` лучше, чем просто завершить программу по Ctrl+C?
   <details><summary>Ответ</summary>

   Обычное завершение обрывает запросы, которые выполняются: клиент не получает ответ, а данные могут остаться
   записанными наполовину. `Shutdown` сначала закрывает приём новых соединений, потом ждёт выполняющиеся запросы (но не
   дольше заданного времени) и только потом возвращает управление.
   </details>

5. (★) Что изменится, если `RequireToken` поставить снаружи: `RequireToken("letmein", RequestID(Logging(log, …)))`?
   <details><summary>Ответ</summary>

   Запрос без токена остановится в `RequireToken` и до `RequestID` и `Logging` не дойдёт: ответ `401` придёт без номера,
   а в логе его не будет. Внешняя обёртка видит **все** запросы, поэтому номера, лог и замер времени ставят снаружи, а
   проверки, которые могут остановить запрос, — внутри них.
   </details>
