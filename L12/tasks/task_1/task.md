# L12 / Task 1 — DataShifter: конвертер JSON → CSV

## Контекст

Аналитикам приходят выгрузки товаров в JSON, а работать они привыкли с таблицами. Тебе поручено написать приложение
**DataShifter**, которое превращает выгрузку в CSV-файл, открывающийся в Excel и Google Таблицах.

Приложение будет работать без присмотра, поэтому к нему три требования: оно **записывает в лог**, что делает; формат
лога **настраивается снаружи**, без правки кода; логика конвертации **не привязана к файлам**, чтобы её можно было
запустить откуда угодно. В следующих ДЗ мы будем это приложение доращивать, поэтому пиши его аккуратно.

Заново писать логгер, middleware и запуск сервера не нужно: они уже есть в твоём решении L11. Мы подключим packages
`shop/logging`, `shop/middleware` и `shop/server` как обычную зависимость. **Для базовой части из L11 нужны модуль
`shop` (его `go.mod`) и `logging.New` (шаг 1 L11), для ★ — ещё `middleware` и `server`.** ★ из L11 не нужны.

Рассчитывай примерно на 3 часа на базовую часть. Только стандартная библиотека Go.

## Из чего состоит приложение

```
база:       input.json ──os.Open──▶ ConvertJSONtoCSV(r, w) ──▶ output.csv    (★★★: через WriteFileAtomic)
★ server:   curl POST /convert ──r.Body──▶ ConvertJSONtoCSV ──w──▶ CSV в ответе
            (server.Run + RequestID + Logging — packages shop/server и shop/middleware из L11)
лог везде:  logging.New(io.MultiWriter(os.Stdout, app.log), LOG_FORMAT)    ← shop/logging из L11
```

| Файл           | Что в нём                                                        | Когда  |
|----------------|------------------------------------------------------------------|--------|
| `go.mod`       | `module task1`, `require shop` и `replace` на `../../L11/task_1` | база   |
| `converter.go` | `ConvertJSONtoCSV` — без файлов и логов                          | база   |
| `main.go`      | логгер, выбор режима, открытие файлов, коды выхода               | база   |
| `server.go`    | маршрут `POST /convert` и вызов `server.Run`                     | ★     |
| `atomic.go`    | `WriteFileAtomic`                                                | ★★★ |

## Подключаем код из L11

В твоём репозитории рядом лежат две папки: `L11/task_1` (модуль `shop`) и `L12/task_1` (наше приложение). Go умеет брать
модуль из соседней папки без интернета, если в `go.mod` написать `replace`. Из папки `L12/task_1`:

```bash
go mod init task1
go mod edit -require=shop@v0.0.0 -replace=shop=../../L11/task_1
```

В `go.mod` появятся две строки (запись `v0.0.0` — просто заглушка: версию заменяет `replace`):

```
require shop v0.0.0
replace shop => ../../L11/task_1
```

После этого packages L11 импортируются по имени модуля: `import "shop/logging"`. Править код в `L11/task_1` из этого ДЗ
не нужно. Если в L11 что-то пришлось поправить, поправь там, и изменение подхватится само.

## Базовое задание

Программа запускается в папке, где лежит файл `input.json`, и делает три шага:

1. Открывает `input.json`.
2. Конвертирует данные в CSV.
3. Записывает результат в `output.csv` (если файл есть, он перезаписывается).

### Формат данных

Вход — JSON-массив объектов:

```json
[
  {
    "id": 1,
    "name": "Чайник",
    "price": 2990,
    "in_stock": true
  },
  {
    "id": 2,
    "name": "Кастрюля, 3 л",
    "price": 1590,
    "in_stock": false
  },
  {
    "id": 3,
    "name": "Ложка",
    "price": 120,
    "in_stock": true
  }
]
```

- Поля: `id` — целое, `name` — строка, `price` — целое, `in_stock` — `true` или `false`.
- Если поля в объекте нет, берётся нулевое значение: `0`, пустая строка, `false`. Лишние поля игнорируются.
- Товары не проверяются и не отбрасываются: строка с ценой `0` или пустым названием тоже попадает в CSV (`Validate` из
  L10–L11 здесь не нужен). Дробное число в `id` или `price` и строка вместо числа — некорректный JSON: ошибка и код `1`.
- Пустой массив `[]` — корректный вход: в CSV будет одна шапка, `rows` равно `0`.

Выход — `output.csv`: сначала шапка `id,name,price,in_stock`, затем по одной строке на объект, в том же порядке.
Логическое значение пишется словами `true` и `false`:

```csv
id,name,price,in_stock
1,Чайник,2990,true
2,"Кастрюля, 3 л",1590,false
3,Ложка,120,true
```

Кавычки вокруг `"Кастрюля, 3 л"` ставит `encoding/csv`: в названии есть запятая.

### Требования

**1. Конвертация не знает про файлы.** Напиши в файле `converter.go` функцию со **строго такой** сигнатурой:

```go
func ConvertJSONtoCSV(r io.Reader, w io.Writer) (rows int, err error)
```

Она читает JSON из `r`, пишет CSV в `w` и возвращает число записанных строк данных (без шапки). Файлов, `os` и логов
внутри неё нет. Сначала разбери весь JSON, потом пиши CSV: если JSON некорректен, функция возвращает `0` и ошибку и
**ничего не пишет в `w`**.

Читай JSON так же, как на слайде про JSON-файл (L12): `json.NewDecoder(r).Decode(&items)`. `io.ReadAll` не нужен ни
здесь, ни в режиме сервера: `Decoder` сам читает из любого `io.Reader`.

Число строк возвращается затем, чтобы `main` мог записать его в лог.

**2. Лог в два места.** Логи пишутся одновременно в файл `app.log` и в `os.Stdout`. Файл открывается так, чтобы старые
строки не стирались: каждый запуск дописывает новые (L12, `O_APPEND`). Логгер создаёт **`logging.New` из L11**, а два
места назначения соединяет `io.MultiWriter`.

В лог попадают:

- запуск приложения;
- открытие `input.json` и создание `output.csv`;
- число обработанных строк — атрибут `rows`;
- ошибка, если она случилась (уровень `ERROR`);
- успешное завершение.

Тексты сообщений придумай сам. Число строк и успешное завершение можно записать одной строкой, как в примере ниже
(`msg=готово rows=3`). Тесты тексты не сравнивают. Они проверяют, что каждая строка `app.log` есть и в консоли, что у
каждой строки нужный формат (см. требование 3), что есть строка уровня `INFO` с атрибутом `rows` и что при ошибке есть
строка уровня `ERROR`.

**3. Формат лога — через переменную окружения `LOG_FORMAT`** (её значение просто передаётся в `logging.New`):

| `LOG_FORMAT`                                        | Формат каждой строки лога (и в консоли, и в файле)     |
|-----------------------------------------------------|--------------------------------------------------------|
| `json`                                              | JSON: `{"time":"…","level":"INFO","msg":"…","rows":3}` |
| `text`, не задана, пустая или любое другое значение | обычный текст: `time=… level=INFO msg=… rows=3`        |

Запуск:

```bash
LOG_FORMAT=json go run .
go run .                 # текстовый формат
```

**4. Ошибки.** Нет `input.json`, некорректный JSON или нельзя создать `output.csv` — программа пишет ошибку в лог
уровнем `ERROR` и завершается с кодом `1`. Успешный запуск завершается кодом `0`.

### Пример

В папке лежит `input.json` из примера выше. Запуск `LOG_FORMAT=json go run .` печатает в консоль (время у тебя будет
другим) и дописывает в `app.log` такие строки:

```
{"time":"2026-10-31T15:46:39.092657+03:00","level":"INFO","msg":"запуск"}
{"time":"2026-10-31T15:46:39.093056+03:00","level":"INFO","msg":"открыт файл","name":"input.json"}
{"time":"2026-10-31T15:46:39.093507+03:00","level":"INFO","msg":"создан файл","name":"output.csv"}
{"time":"2026-10-31T15:46:39.093701+03:00","level":"INFO","msg":"готово","rows":3}
```

Файл `app.log` дописывается, поэтому после запусков в двух форматах строки в нём перемешаются: перед сменой формата
удали его.

Без `LOG_FORMAT` те же события выглядят так:

```
time=2026-10-31T15:46:38.590+03:00 level=INFO msg=запуск
time=2026-10-31T15:46:38.590+03:00 level=INFO msg="открыт файл" name=input.json
time=2026-10-31T15:46:38.595+03:00 level=INFO msg="создан файл" name=output.csv
time=2026-10-31T15:46:38.596+03:00 level=INFO msg=готово rows=3
```

### Как решать

1. Сначала напиши `ConvertJSONtoCSV` и проверь её без файлов: `strings.NewReader` на входе и `os.Stdout` на выходе.
   Объяви в `converter.go` свой struct `Item` с полями `ID`, `Name`, `Price`, `InStock` и тегами `json` (`id`, `name`,
   `price`, `in_stock`), как `Product` в каталоге L11. Сам package `shop/catalog` не импортируй: DataShifter про каталог
   не знает. Список — `[]Item`, как на слайде про JSON-файл (L12). CSV пишет `csv.Writer`: `Write` для каждой строки, в
   конце `Flush` и проверка `cw.Error()` (L12), где `cw` — твой `csv.Writer`. Числа в строки переводит `strconv.Itoa`,
   булево — `strconv.FormatBool`.
2. Потом подключи логгер: `os.OpenFile("app.log", os.O_APPEND|os.O_CREATE|os.O_WRONLY, 0644)`,
   `io.MultiWriter(os.Stdout, file)`, затем `logging.New(out, os.Getenv("LOG_FORMAT"))` из L11. Готовый логгер сделай
   главным через `slog.SetDefault`, дальше везде используй `slog.Info` и `slog.Error`.
3. В `main` открой файлы, вызови `ConvertJSONtoCSV(in, out)` и залогируй результат. Каркас `main.go`:

   ```go
   func main() {
       // 1. открой app.log (logFile), собери логгер из logging.New и сделай его главным через slog.SetDefault
       // 2. slog.Info("запуск")
       if err := run(); err != nil {
           slog.Error("ошибка", "err", err)
           logFile.Close() // os.Exit не выполняет defer, поэтому закрываем app.log сами
           os.Exit(1)      // только в самом конце main, после записи ошибки в лог
       }
   }

   func run() error {
       // открой input.json, создай output.csv, вызови ConvertJSONtoCSV, залогируй rows
       return nil
   }
   ```

### Подсказки

- **Не используй `log.Fatal` и `os.Exit` посреди `main`:** они завершают программу, не выполняя `defer`, и файлы
  закроются не вами. Удобнее вынести работу в `func run() error`: её `defer` выполнятся при возврате. А в `main` запиши
  ошибку в лог, закрой `app.log` сам и только потом вызови `os.Exit(1)`.
- **Логгер нужен до первой записи в лог.** Если открыть `app.log` не удалось, лог писать некуда: выведи сообщение в
  `os.Stderr` и завершись с кодом `1`.
- **`defer file.Close()` ставь сразу после проверки ошибки открытия** (L12).

## ★ Задание со звёздочкой: приём JSON по сети

Аналитики хотят отправлять выгрузки автоматически, из других систем. Добавь в приложение режим сервера. Почти всё для
него уже написано в L11: сервер, нумерация запросов и лог запросов берутся из packages `shop/server` и `shop/middleware`.

**Режим выбирается переменной окружения `MODE`:**

- не задана или любое другое значение — работает как раньше (читает `input.json`, пишет `output.csv`);
- `MODE=server` — вместо файла запускается HTTP-сервер.

Сервер слушает адрес из переменной окружения `ADDR` (если она пуста — `:8080`) и обрабатывает `POST /convert`:

- тело запроса — JSON-массив в том же формате;
- ответ — CSV, заголовок `Content-Type: text/csv; charset=utf-8`, код `200`;
- если тело — некорректный JSON, ответ `400`, а ошибка попадает в лог (`ERROR`).

Пример проверки:

```bash
MODE=server go run .
# в другом терминале:
curl -X POST --data-binary @input.json localhost:8080/convert
```

### Что обязательно

1. **В режиме сервера никаких временных файлов и `io.ReadAll`.** Нельзя сохранять присланный JSON на диск и нельзя
   сначала прочитать всё тело в `[]byte`.
2. **Передай `r.Body` и `w` прямо в `ConvertJSONtoCSV`:** `r.Body` — это `io.Reader`, а `http.ResponseWriter` —
   `io.Writer` (L11). Код функции из базового задания не меняется ни на строчку: в этом смысл первого требования.
3. **Сервер, номера и лог запросов заново не пиши — бери из L11.** Сам пишешь только маршрут: `mux := http.NewServeMux()`
   и `mux.HandleFunc("POST /convert", …)`. Запуск и остановку делает `server.Run`, обёртки вкладываются друг в друга:
   `middleware.RequestID(middleware.Logging(log, mux))`. В логе у каждого запроса будут `method`, `path`, `status` и
   `duration`, а у ответа — заголовок `X-Request-ID`. Лог идёт в те же два места и в том же формате, что в базовом
   задании: передай в `server.Run` и `middleware.Logging` тот же логгер.
4. **Ctrl+C останавливает сервер аккуратно.** Об этом заботится `server.Run`: тебе остаётся передать ей контекст, как в
   `main.go` L11: `signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)`.
5. **Заголовок `Content-Type` ставь до вызова `ConvertJSONtoCSV`:** она сразу пишет тело в `w`, а после первой записи
   заголовки и код уже не поменять (L11: заголовки → код → тело). При ошибке функция ничего не записала, поэтому
   `http.Error(w, "неверный JSON", http.StatusBadRequest)` ещё успеет поставить `400`. Ошибка здесь — обычный текст,
   а не JSON `{"error":…}`, как в каталоге L11: клиент ждёт CSV, а не JSON, и формат ошибок у каждого сервиса свой.

## ★★★ Задание с тремя звёздочками: безопасная запись `output.csv`

Сейчас `os.Create("output.csv")` стирает файл **сразу**, а данные пишутся потом. Если `input.json` окажется битым,
аналитики останутся с пустым или обрезанным `output.csv`, а вчерашняя выгрузка пропадёт. Сделай запись безопасной (слайд
про временный файл и `Rename`, L12):

1. Напиши в файле `atomic.go` функцию

   ```go
   func WriteFileAtomic(name string, write func(w io.Writer) error) error
   ```

   Она создаёт временный файл **в той же папке** (`os.CreateTemp`), вызывает `write`, делает `Sync`, закрывает файл и
   только потом подменяет им `name` через `os.Rename`. Права итогового файла — `0644`.
2. Если на любом шаге ошибка (включая ошибку из `write`), временный файл удаляется, а старый `name` остаётся нетронутым.
3. Режим «файл → файл» создаёт `output.csv` через `WriteFileAtomic`, передавая в `write` вызов `ConvertJSONtoCSV`.

Проверить можно так: запусти программу на хорошем `input.json`, потом испорти его (убери последнюю скобку) и запусти
снова. Программа завершится с кодом `1`, а `output.csv` останется прежним. Других файлов вроде `output.csv.123.tmp` в
папке быть не должно.

Дерево репозитория, то, что проверяется, и способ сдачи смотри в [README](../../README.md).

## Зачем эта задача

- **Функция работает с `io.Reader` и `io.Writer`, а не с файлами (L12).** Одна и та же `ConvertJSONtoCSV` читает файл,
  тело сетевого запроса или строку в тесте, и в ней не меняется ни строчки.
- **Лог в два места сразу — `io.MultiWriter` (L12).** Консоль нужна, чтобы видеть работу сейчас, файл — чтобы
  разобраться потом.
- **Формат лога задают переменной окружения (L11).** Люди читают текст, программы разбирают JSON. Код один, формат
  выбирают при запуске.
- **Готовый код подключают как зависимость.** Логгер из L11 принимает `io.Writer`, поэтому ему всё равно, куда писать: в
  консоль, в файл или в оба места сразу. Такой код не переписывают под каждое приложение.
- **Ошибки возвращаем наверх (L7).** Что с ними делать — решает `main`: записать в лог и завершить программу с кодом 1.

## Проверь себя

1. Почему `ConvertJSONtoCSV` принимает `io.Reader` и `io.Writer`, а не имена файлов?
   <details><summary>Ответ</summary>

   Функция не знает, откуда пришли данные и куда они идут. В базовом задании это файлы, в ★ — тело запроса и ответ
   сервера, в проверке — строка и буфер в памяти. Если бы внутри был `os.Open("input.json")`, для сервера пришлось бы
   писать вторую функцию.
   </details>

2. Зачем писать лог и в консоль, и в файл?
   <details><summary>Ответ</summary>

   В консоли видно, что программа делает сейчас. Файл остаётся, когда консоль закрыта: из него потом понятно, что и
   когда происходило. `io.MultiWriter` соединяет оба места в один `io.Writer`, а `slog` не знает, что их два.
   </details>

3. Почему формат лога выбирают переменной окружения, а не правят в коде?
   <details><summary>Ответ</summary>

   Один и тот же собранный файл работает по-разному: на ноутбуке разработчика читать удобнее текст, на сервере логи
   собирает другая программа, и ей нужен JSON. Пересобирать программу ради этого не надо: достаточно запустить с другим
   `LOG_FORMAT`.
   </details>

4. (★) Зачем передавать `r.Body` прямо в `ConvertJSONtoCSV`, а не читать его через `io.ReadAll`?
   <details><summary>Ответ</summary>

   Память это почти не экономит: `Decode` тоже сначала собирает весь JSON-массив в своём буфере и только потом строит
   список. Дело в другом: `ConvertJSONtoCSV` уже умеет читать из любого `io.Reader`, а `r.Body` — такой же `io.Reader`,
   как файл. `io.ReadAll` — лишний шаг: тело копируется в `[]byte`, а потом его всё равно придётся снова превратить в
   `io.Reader` (`bytes.NewReader`), чтобы передать в функцию.
   </details>

5. (★★★) Почему нельзя просто записать данные в `output.csv` напрямую, а нужен временный файл и `Rename`?
   <details><summary>Ответ</summary>

   `os.Create` стирает старое содержимое **до** того, как мы узнали, получится ли конвертация. Ошибка посреди записи
   оставляет битый файл, и вчерашней выгрузки уже нет. Временный файл рядом: пишем туда, и только когда всё получилось,
   `Rename` подменяет им старый целиком. Читатель видит либо старый файл, либо новый, но не половину. `Sync` перед
   подменой не даёт отключению питания оставить под новым именем пустой файл.
   </details>

6. Что даёт подключение L11 через `replace`, по сравнению с копированием файлов в L12?
   <details><summary>Ответ</summary>

   Код живёт в одном месте. Нашёл ошибку в `middleware` и поправил в L11: приложение L12 получает исправление сразу, без
   правки копий. Заодно ясно видно, что package `logging` не зависит от приложения, которое им пользуется. Так же
